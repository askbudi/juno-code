# Create task workflow

Own task/PDR creation. Execute only when the request also authorizes implementation or explicitly requests workflow execution. Task creation alone never authorizes product edits, local integration, release, push, publication, deployment, production mutation, restart, or E2E.

1. Resolve the canonical controller with `controller_resolver.py --operation diagnostic`; Juno never silently switches refs. Product commands receive the admitted worktree as `TASK_ROOT`, while controller Kanban/session writes remain routed through `JUNO_TASK_ROOT`. Read the task-creation, review, and lifecycle wikis.
2. Write empty-context task bodies and one symbolic manifest covering task/dependency identity, exact target refs and bases, expected paths, validation, risk, budgets/timeouts, artifact root, cleanup owner, and separately reserved E2E. Every product mutation uses a named exact-base worktree.
3. Retain the current `schema_version: 2`, `workflow_class: local_integration`, orchestration workspace, declared risk, integration step, terminal gate, exact automatic queue/channel/rebuild/detach policy, validation ownership, typed receipts, direct argv-list integration owner, candidate read-only identity, and actual-target evidence required by the shipped runtime. Reference receipt locations through `{{ receipts.<id>.path }}` or `JUNO_WORKFLOW_RECEIPT_<ID>`, never duplicate hardcoded paths. Do not emit a future schema or command before it exists.
4. Generate a lean phase graph: deterministic admission; implementation with focused tests; `REVIEW_READY` validation with one exact-tip full suite; independent semantic review; deterministic candidate preparation; expected-SHA integration; actual-target truth; typed cleanup; compact terminal result. Do not add standalone `implementation_guard`, `pre_merge_guard`, or `candidate_guard` steps.
5. High-risk work declares two fresh read-only review steps, Reviewer A followed by Reviewer B, bound to the same frozen base and tip. Both steps must be able to finish even when one reports a finding. A later gate waits for both outputs. No implementation, repair, or product commit may run between them. Low/medium work declares the project-required one fresh independent review.
6. Render both high-risk reviews from `.juno_task/prompts/review_commit_parallel_runner.md`. Reviewers do not edit, commit, update Kanban, launch reviewers, or repair. Only the logical orchestrator launches reviews; a separate repair step consumes one consolidated packet after both results.
7. Run full suites only at review-ready candidate boundaries. Review steps consume exact-tip evidence and use bounded diagnostics rather than rerunning broad suites by default. Long-running steps expose one bounded wait/result and artifact pointers rather than encouraging repeated polling.
8. Declare project canonical task-body validators as argv lists and run `task_workflow_helper.py create-task-set` dry-run before `--execute`. Read tasks back and lint the generated workflow before dispatch.
9. Keep current candidate, target-movement, integration, actual-target, recovery/amendment, and cleanup mechanics accurate until the final hard cut. No adapter or second runtime is created by this instruction patch.

If execution is not authorized, stop after the handoff. Otherwise consume the exact generated artifacts without recreating tasks or manually rewriting review prompts.
